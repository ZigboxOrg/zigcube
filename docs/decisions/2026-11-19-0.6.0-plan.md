# The plan to ship Zigbox 0.6.0 and Zigcube 0.6.0

*Decided 2026-11-19, by the owner (on the supervisor's proposal). The same file is in both
repositories.*

## Decisions

1. **Rescue.** Every branch of the suspended `Zigbox/zigbox`, `Zigbox/zigcube` and
   `Zigbox/zigcube-jepsen` (but `vm/*`) is in the new repositories under `old/<name>`
   (`old/jepsen/<name>` in zigcube for the Jepsen harness). The old tags could not be pushed from a
   session; the owner pushes them (the supervisor's report has the commands). Restored work starts
   from these branches.
2. **Release signal.** For 0.6.0, GitHub's `ci` workflow keeps running on pushes to `main`, so
   `release.yml` (which starts on `ci` and renders its evidence table from that run) works as it
   is. Pull requests run on Woodpecker. Teaching the release workflow to read Woodpecker comes
   after 0.6.0.
3. **Zigcube 0.6.0 scope** is C3 + C4 + C5 slices 1 and 2 (the public TLS server and sealing). C5
   slices 3a onward (ACME, the edge, sim-c5, demo-c5) move to 0.7.0. This supersedes the scope in
   `2026-11-15-0.6.0-bundles-c3-c4-c5.md` (Zigcube); its other terms (Jepsen-gated, the soak) stand.
4. **Order.** Zigbox 0.6.0 (S2, lazy start) ships first; Zigcube 0.6.0 pins Zigbox's 0.6.0 release
   commit. Nothing in Zigcube's scope waits on S2 (ZB-1/ZB-2 shipped earlier).
5. **The Fable review is at RC1.** When a product is feature complete, its commit is RC1, and a
   Fable session reviews the whole product (design, security, testing) as the last measure before
   the final gates. Its findings are fixed by fresh sessions. Then the final gates run on the
   release commit: Zigbox the extended fuzz run; Zigcube Jepsen and the 24-hour fleet soak. The
   second independent release review (Opus, on the diff since the last release, as AGENTS.md
   requires) runs at RC1 too, without reading the Fable review. This replaces the "whole-product
   review before the release reviews" of `2026-11-16-0.6.0-first-public-preview.md` in timing
   only.

## Three lanes

Three implementer sessions work at all times, one per lane, a fresh session per slice; the
supervisor reviews each slice (a GitHub review on its pull request) and merges. Mechanical parts
go to Haiku. When a lane runs dry it takes work from another.

**Lane A: Zigbox to RC1**
- A1. Land the restored backlog: a pull request of `claude/stoic-carson-jnfdb1` up to f333434 (the
  `.github` restore, the release-evidence table, the top-20 suite, `.gitignore`, GitButler; and
  removing `.DS_Store`), merged with a merge commit so f333434 (Zigcube's pin) stays on `main`.
  Then the Woodpecker work and `ops/backup/` as their own pull requests.
- A2. `Zigbox/` to `ZigboxOrg/` in workflows, runbooks and live links (Haiku); history links stay.
- A3. S2 slice 6: `demo-s2` (brief `docs/briefs/S2-lazy-start.md`).
- A4. `--lazy` on: the build option and the E0004 refusal go; goldens, help, the errors site.
- A5. RC1, then the Fable review's fixes; release notes, version, README and site.

**Lane B: Zigcube to RC1**
- B1. Land the new pin (`claude/stoic-carson-jnfdb1`), restore `.gitignore`, `.claude/hooks/` and
  `.claude/settings.json` from `old/main`, remove the `.DS_Store` files; `ci` green on `main`.
- B2. One pull request each: `restore/fencing-contract`, `claude/charming-archimedes-9fgzqf` (the
  J12 fix), `restore/c5-slice2`.
- B3. C3: bring `old/claude/c3-demo` up to `main`, demo-c3 green, then slices 13 to 15.
- B4. C4: slices 1 to 5 from `old/claude/c4-slice5`, then 6 to 12.
- B5. The five 0.5.2 carry-over findings (`2026-11-17-0.5.2-known-issues-to-0.6.0.md`), between
  the larger items.

**Lane C: gates and infrastructure, both repositories**
- C1. One re-runnable script for the owner's ZigboxOrg setup: the release GitHub App, the
  `release` and `release-publish` environments, signing and Mac secrets, Google WIF (Zigbox's
  demo-m6d and Zigcube's Jepsen), and the old tags.
- C2. The simulation fleet on ZigboxOrg (repo defaults, token, tracker, redeploy); sim-c4 workers
  once C4 lands.
- C3. Jepsen: `ZigboxOrg/zigcube-jepsen` from `old/jepsen/*`, the WIF condition, the mTLS client
  fix, a full passing run; the C4 grant property after B4.
- C4. Zigcube on Woodpecker; the 0.5.3 retro's fuzz sharding (`provenance`, `lazy_resolver`).
- C5. At each release: the extended fuzz shards (Zigbox), the soak and Jepsen (Zigcube) on the
  release commit.

## Release sequence, per product

Feature complete → RC1 → the Fable review and the Opus review → fixes → final gates (above) →
release notes and status → `release.yml` and the owner's approval → retro within a day.
